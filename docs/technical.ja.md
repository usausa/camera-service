# 🔧 技術資料

🌐 [English](technical.md) | 日本語

カメラの仕様を先に、次にアプリケーションの仕様を記載。導入と設定は [README](../README.ja.md)。

## 📷 カメラ

### 🔎 デバイスと形式

- ソースがすべてカラーのデバイスをカメラとして扱う。複数(プレビューと録画)あれば最初を使用。赤外線カメラとセンサーグループは対象外
- カメラのデバイス: `DeviceId`、次に `Device`、指定がなければ形式が合う最初のデバイス。指定したデバイスは置き換えない
- 形式はピクセル形式、サイズ、フレームレート(0.5 fps 以内)で照合。ピクセル形式は YUY2 と NV12
- デバイスと形式は最初に開くときと失敗後に解決
- 排他: 他のアプリの使用中は、開いた後にキャプチャーが失敗

### 🎨 色

- 範囲はカメラの形式に従い、情報がなければビデオ範囲。マトリックスは BT.601
- JPEG: YUY2 とビデオ範囲の NV12 はフル範囲の NV12 に変換し、フル範囲の NV12 はそのままエンコード
- H.264: カメラの範囲のまま渡し、ヘッダーで送信。ブラウザーがデコーダーに範囲とマトリックスを指定し、どのエンコーダーでも JPEG と同じ色

### 🔄 開閉

- 利用者(クライアント、静止画、保存)がカメラを借りる。最初の 1 人ですぐ開き、最後の返却から `IdleTime` で閉じる
- 最初の `WarmupTime` のフレームは使わない(露出の安定待ち)
- 保存は予定の `WarmupTime` + 2 秒前にカメラを借りる
- 静止画と保存はフレームを最大 `WarmupTime` + 10 秒待ち、来なければ失敗(静止画は 503)
- 手順(開く、閉じる、再試行、フレームの監視)は 0.5 秒のタイマーで 1 つずつ
- デバイス検索、開く、閉じるは 15 秒で打ち切り。閉じるときは必ずカメラを解放

### ⚠️ 失敗

- 失敗: 開く、閉じるの失敗、カメラのエラー、`FrameTimeout` の間フレームなし、手順の想定外の例外
- カメラを閉じ、5 → 10 → 30 → 60 秒後に開き直す。借りる人がいる間のみ
- 次のフレームまで失敗のまま: 開けてもフレームが来なければ、間隔は伸び続け `/health` は 503
- 再試行を待つ間の保存はすぐ失敗

### 🌙 フレームレート

- カメラのフレーム数は形式より少ない場合あり(暗いと露出が延びるなど)
- 前のフレームの処理中に届いたフレームは飛ばす
- MJPEG と静止画: `Stream:Fps` に間引く
- H.264: 全フレーム。キーフレームの間隔とビットレートは形式のフレーム数で数えるので、フレームが少ないとキーフレームの間隔は延び、ビットレートは下がる
- 保存は予定の時刻以降に撮った最初のフレームを使用

## 🧩 アプリケーション

### 🧱 構成

| プロジェクト | 内容 |
|:--|:--|
| `src/CameraService.Core` | 映像の型とインターフェース、YUV 変換、フレーム共有、焼き込み、画像の名前、削除対象(OS 非依存) |
| `src/CameraService.Platform.Windows` | カメラ(MediaFrameReader)、JPEG とサムネイル(WIC)、H.264(Media Foundation) |
| `src/CameraService.Host` | サービス本体(ASP.NET Core、Blazor Server) |
| `tests/CameraService.UnitTests` | Core と Platform.Windows |
| `tests/CameraService.IntegrationTests` | テスト用カメラのサーバー |
| `tools` | サービスの登録と削除 |

- Windows の API は Platform.Windows のみ。`AddWindowsPlatform()` で Core のインターフェースに登録

### 🖼️ JPEG と MJPEG

- 待つクライアントがいるときだけエンコード。1 回を全クライアントで共有(最新の 1 枚のみ)
- エンコーダーのエラーはログに記録し、10 秒後に新しいエンコーダーで再試行
- カメラを閉じるとエンコーダーとバッファを解放
- 各フレームの直後に次の区切りを送信
- `?raw`: 同じ内容で `Content-Type: application/octet-stream`。`fetch` 用
- ライブ: `fetch` + canvas。デコードが遅れたら最新の 1 枚のみ。ページを離れると要求を中止
- 停止時: MJPEG を終了し、新しい要求は 503

### 🎞️ H.264

- **エンコーダー:** ハードウェア優先、次に Windows のソフトウェア。低遅延、CBR、B フレームなし、Main プロファイル
- **生存期間:** カメラごと。最初のクライアントでバックグラウンド作成、クライアントなしが 10 秒で解放
- **失敗:** クライアントを `InternalServerError` で閉じ、画面は MJPEG に切り替え、`/health` は `Degraded`。10 秒後か新しいクライアントで再試行
- **フレーム:** YUY2 は範囲を変えず NV12 に並べ替え。1 回を共有
- **キーフレーム:** `Stream:H264:KeyFrameInterval` ごと。接続直後とフレーム飛ばしの後は、エンコーダーに要求したキーフレームまで送らない(500 ms に 1 回まで)。ブラウザーもデコードエラーとキューあふれのときにテキストで要求
- **画面:** localhost か HTTPS で `VideoDecoder` があれば H.264、なければ MJPEG。`NotSupportedError` でも MJPEG
- **停止:** 停止の開始時に接続を閉じる(`EndpointUnavailable`)

### 📡 WebSocket プロトコル

- サーバー: フレームごとにバイナリー(ヘッダー + Annex B のアクセスユニット)。最初はキーフレーム
- クライアント: テキストはすべてキーフレームの要求
- 閉じる状態: `InternalServerError`(1011、エンコーダーなし、画面は MJPEG)、`EndpointUnavailable`(1001、停止、画面は再接続)
- `Stream:H264:Enable` が `false` なら 404、WebSocket 以外は 400

ヘッダー(リトルエンディアン、32 バイト):

| 位置 | 型 | 内容 |
|--:|:--|:--|
| 0 | uint16 | バージョン(1) |
| 2 | uint16 | ヘッダー長(データの位置) |
| 4 | uint16 | 幅 |
| 6 | uint16 | 高さ |
| 8 | uint32 | カメラのフレーム番号 |
| 12 | uint32 | フラグ(bit 3: キーフレーム、bit 4: フル範囲で BT.601 マトリックス、それ以外はビデオ範囲) |
| 16 | float64 | 撮影時刻(Unix ms) |
| 24 | float64 | エンコード時刻(Unix ms) |

### 🔌 接続断

MJPEG と H.264 で同じ。ページの再読み込みなし。

- **切断:** 1 秒後に再接続。最後のコマを残し `Reconnecting` を表示
- **切断の通知なし(ネットワーク断):** データなしが 5 秒で `Reconnecting`、15 秒で再接続
- フレームを送らないカメラでも同じ動作

### 💾 保存

予定は現地時刻の Cron 式。実行できなかった回は飛ばす。

1. カメラを借りる
2. 予定の時刻以降に撮った最初のフレームをフル範囲の NV12 で複写
3. 撮影時刻を焼き込み、`Snapshot:Quality` でエンコード
4. `.tmp` に書いて `{保存先}\yyyyMMdd\HHmmss.jpg` に置き換え
5. カメラを返す

- 焼き込み: 自前の 7 ドットのビットマップフォント、白文字に黒の縁取り、その下の色差は無彩色、余白は `Scale` × 4 ドット、画像の端で切れる
- 削除は空き容量が不明になると警告して停止

### 🖼️ サムネイルとキャッシュ

- **キャッシュ:** `Cache-Control: private, max-age=86400`、ファイルの時刻と大きさの `ETag`、一致で 304
- **サムネイル:** 縮小した YCbCr 面でデコードし、色変換なしでエンコード。幅約 320、デコーダーの倍率(1/2、1/4、1/8)。品質 80、メモリーに 64 MB まで(使用が少ないものから削除)
- **拡大:** 次の 3 枚を先読み
- **削除された画像:** 404

| 元の画像 | サムネイル |
|:--|:--|
| 640x480 | 320x240 |
| 1280x720 | 320x180 |
| 1920x1080 | 480x270 |
