## 🔄 カメラを開く・閉じる

- 使う側(MJPEG と H.264 のクライアント、静止画の要求、定期保存)がカメラを借りる。最初の 1 人で開き、最後の 1 人が返してから `IdleTime` で閉じる
- 開いてから `WarmupTime` のフレームは使わない
- 失敗(開けない、閉じられない、エラー、`FrameTimeout` の間フレームが来ない)のときは閉じて開き直す。間隔は 5 → 10 → 30 → 60 秒。借りる人がいない間は開き直さない
- 次にフレームが来るまでは失敗のまま(開けてもフレームが来なければ、間隔は伸び続け、`/health` も戻らない)
- デバイスを探す、開く、閉じるは 15 秒で打ち切って失敗にする(ドライバーが返らなくても、カメラの手順とサービスの停止が止まらない)。閉じるときの例外でも、読み取りとキャプチャーは解放する
- デバイスと形式は最初に開くときに探し、失敗のあとに探し直す
- 開く・閉じる・開き直すは 0.5 秒ごとのタイマーで 1 つずつ進める(最初の 1 人のときはすぐ)
- カメラは排他で開く。ほかのアプリが使っている間は、開いたあとで失敗する(`0xC00D3704`)。定期保存はその回を失敗にしてログと `/health` に出し、カメラが空いたあとの保存で元に戻る

## 🖼️ JPEG と MJPEG

- カメラのスレッドで、待っているクライアントがいるときだけ `Stream:Fps` に間引いてエンコード。1 回のエンコードを全クライアントで共有(最新の 1 枚だけを渡す)
- YUY2 や範囲の狭い NV12 は、フル範囲の NV12 にしてから WIC でエンコード
- 作業用のバッファに書いてから実際の大きさのフレームに写す。フレームごとに最大の大きさ(640x480 で約 0.9 MB)のバッファを持たない
- カメラを閉じると、エンコーダーとバッファも手放す
- MJPEG は各フレームの後にすぐ次の区切りを送る(ブラウザーは次の区切りが来てから表示する)
- `stream.mjpg` に `?raw` を付けると、中身は同じで `Content-Type` が `application/octet-stream`。画面の `fetch` が使う(ブラウザーによっては、画像以外の multipart の応答を断る)
- 画面のライブは `fetch` で読んで canvas に描く(`img` だと切断が分からない)。デコードが遅れたら最新の 1 枚だけを描く。画面を離れると `fetch` を中止して接続を切る
- サービスを止めるときは、MJPEG を終え、止め始めてからの要求は 503 で断る(画面はつなぎ直そうとするので、断らないと新しい接続が残り、止まるまで 30 秒待つことになる)

## 🎞️ H.264

tool-camera の H.264 配信(Media Foundation のエンコーダー、WebSocket、WebCodecs)を移した。

- **エンコーダー:** ハードウェア(NVENC など)を先に試し、使えなければ Windows 標準のソフトウェア。低遅延モード、CBR、B フレームなし、Main プロファイル。ビットレートは解像度から決める(640x480 まで 4 Mbps、1280x720 まで 8 Mbps、それより上 16 Mbps)
- **作成と解放:** カメラごとに、最初のクライアントが来たときにバックグラウンドで作る(NVENC は 0.3〜0.6 秒)。クライアントがいない状態が 10 秒続いたら解放する(0.5 秒ごとのタイマーで見るので、カメラが閉じていても解放する)
- **失敗:** 作れない・動かなくなったときは、つないでいるクライアントを `InternalServerError` で閉じ、画面は MJPEG に切り替える。理由はカメラのページと状態のページに出し、`/health` は `Degraded`。10 秒後か、新しいクライアントが来たときに作り直す
- **フレーム:** カメラのフレームを全部(間引かずに)エンコードする。YUY2 は範囲を変えずに NV12 に並べ替えて渡す。1 回のエンコードを全クライアントで共有する
- **キーフレーム:** 2 秒ごと(`Stream:H264:KeyFrameInterval`)。接続した直後と、送信が遅れてフレームを飛ばしたあとは、次のキーフレームまで送らずにエンコーダーに要求する(500 ms に 1 回まで)。ブラウザーもデコードのエラーやキューのあふれのときに、テキストのメッセージで要求する
- **色:** カメラの範囲のまま渡し、範囲をヘッダーで送る。ブラウザーはデコーダーに範囲と BT.601 のマトリックスを指定するので、どのエンコーダーでも JPEG と同じ色になる
- **画面:** localhost か HTTPS で `VideoDecoder` があれば H.264、なければ MJPEG。デコードできない設定(`NotSupportedError`)のときも MJPEG に切り替える
- **止めるとき:** H.264 の接続は止め始めに閉じる(`EndpointUnavailable`)

### WebSocket のプロトコル

- サーバーからは、フレームごとにバイナリーのメッセージ(ヘッダー + Annex B のアクセスユニット)を送る。最初のメッセージはキーフレーム
- クライアントからのテキストのメッセージ(中身は何でもよい)は、キーフレームの要求
- サーバーが閉じるときの状態: `InternalServerError`(1011。エンコーダーがない。画面は MJPEG に切り替える)、`EndpointUnavailable`(1001。止めるとき。画面はつなぎ直す)
- `Stream:H264:Enable` が `false` なら 404、WebSocket でない要求は 400

ヘッダー(リトルエンディアン、32 バイト。tool-camera のヘッダーから検出の部分を除いた形)

| 位置 | 型 | 内容 |
|--:|:--|:--|
| 0 | uint16 | バージョン(1) |
| 2 | uint16 | ヘッダーの長さ(データの位置) |
| 4 | uint16 | 幅 |
| 6 | uint16 | 高さ |
| 8 | uint32 | カメラのフレームの連番 |
| 12 | uint32 | フラグ(bit 3: キーフレーム、bit 4: フル範囲で BT.601 のマトリックス。立っていなければビデオ範囲) |
| 16 | float64 | 撮った時刻(Unix ms) |
| 24 | float64 | エンコードした時刻(Unix ms) |

## 🔌 接続が切れたとき

MJPEG と H.264 で同じ。画面は再読み込みなしで戻る。

- **切れたとき:** 1 秒後につなぎ直す。映像は最後のコマのまま残り、右上の表示を赤い `Reconnecting` にする
- **切れたことが分からないとき(ネットワークが落ちたなど):** データが 5 秒来ないと `Reconnecting` にし、15 秒来ないと接続を閉じてつなぎ直す
- カメラが失敗してフレームが来ないときも同じ動きになる(理由は映像の上に出る)

## 🕒 時刻の指定

- スケジューラー(Mofucat.JobScheduler)は「今の時刻」のオフセットで Cron を計算するので、現地時刻を返す TimeProvider を渡している(UTC のままだと `0 3 * * *` が日本時間の 12 時になる)
- TimeProvider はアプリ全体には登録しない(ほかの部品は UTC を期待する)
- 取りこぼしは Skip(`MisfirePolicy.Skip`)

## 💾 保存の流れ

1. 予定の時刻の `WarmupTime` + 2 秒前(既定 3 秒前)にカメラを借りる。閉じていれば開く
2. 予定の時刻より後に撮ったフレームのうち最初の 1 枚を写して、フル範囲の NV12 にする(カメラのスレッド。届くまでの遅れの分、予定の時刻の直後に届いたフレームでも、撮ったのは予定の時刻より前のことがあるので、撮った時刻で選ぶ)
3. 日時を焼き込み、`Snapshot:Quality` で JPEG にする
4. 一時ファイル(`.tmp`)に書いてから、`{保存先}\yyyyMMdd\HHmmss.jpg` に置き換える
5. カメラを返す。ほかに使う人がいなければ `IdleTime` で閉じる

- カメラが失敗の状態(開き直しを待っている間)なら、待たずにその回を失敗にする。フレームが 10 秒来ないときも失敗
- 保存ごとのログは Debug(1 分ごとに Information で出すと多すぎるので)

### 日時の焼き込みの描き方

- 数字と記号だけの自前のビットマップフォント(高さ 7 ドット)。OS のフォントに依存しない
- 白い文字に黒い縁取り。文字と縁取りのところの色差は無彩色にする(背景の色が文字ににじまない)

### 自動削除

- 消している途中で空き容量が分からなくなったら、警告を出してそこで止める
- 対象は全カメラのフォルダー。空き容量はドライブごとに調べる

## 🖼️ サムネイルとキャッシュ

- **キャッシュ:** `Cache-Control: private, max-age=86400` と `ETag`(更新時刻と大きさから作る)。同じ `ETag` の要求には 304 を返す
- **サムネイルの作り方:** WIC の JPEG デコーダーで縮小しながら YCbCr の面にデコードし、そのまま JPEG にする(色の変換はしない)
  - 幅 320 を目安に、デコーダーが選べる大きさ(1/2、1/4、1/8)になる。縮小した色差は輝度と同じ大きさで出てくるので、2x2 を平均して 4:2:0 にする
  - 品質 80。サーバーのメモリーに合計 64 MB まで置く(よく使わないものから消す)
- **保存画像のページ:** 拡大では次の 3 枚を先に読み込む

| 元の画像 | サムネイル |
|:--|:--|
| 640x480 | 320x240(約 17 KB) |
| 1280x720 | 320x180 |
| 1920x1080 | 480x270(1/4。デコーダーが選ぶ) |

- 作る時間: 1 枚約 2〜4 ms(640x480、HTTP を含む)。メモリーにあれば約 2 ms

## ❤️ ヘルスチェックとログ

- 結果はログに出さない(`Microsoft.Extensions.Diagnostics.HealthChecks` を `Fatal` にしている)。呼ぶたびに行が増えるのを避けるため。カメラの失敗、保存の失敗、空き容量の不足は、それぞれのログに出る
- 起動の失敗は `Program.cs` で捕まえて `Fatal` で書き、終了コード 1 で終わる。設定を読むまでは仮のロガーが `..\Log\CameraService_.log` に書くので、設定の JSON の誤りもファイルに残る

## 📊 計測

### カメラと MJPEG

ELECOM 2MP Webcam、YUY2 640x480 30fps、`Stream:Fps` 10、Release。

| 項目 | 値 |
|:--|:--|
| カメラを開く | 0.81〜0.83 秒(デバイスを探す約 0.7 秒を含む。閉じた直後に開き直したときは 0.09 秒) |
| 静止画(閉じているとき) | 1.8〜1.9 秒(開く + `WarmupTime` 1 秒) |
| 静止画(開いているとき) | 71 ms |
| MJPEG | 10 fps、1 枚約 64 KB |
| 閉じるまで | 最後のクライアントから約 10.7 秒(`IdleTime` 10 秒 + タイマー) |
| ライブを止めてから接続が切れるまで | 3〜7 ms |
| CPU(1 コア) | 誰も見ていないとき 0.57 %、MJPEG 1 台 3.6 % |

- 開いた直後の明るさ(フレームの平均): 最初から落ち着いた値に近く、0.3〜0.6 秒に最大 8 % ほど揺れる。`WarmupTime` の既定は 1 秒のまま
- サービスで、誰も見ていないとき(毎分の保存あり)の CPU は 0.33 %
- 止めるまで: 画面を開いたままでも 1.5 秒(止め始めてからの要求を断る前は 31.5 秒)

### MJPEG と H.264

同じ 640x480、クライアント 1 台ずつ、Release、サービス。

| 方式 | fps | ビットレート | 1 フレーム | サーバーの CPU(1 コア) |
|:--|--:|--:|--:|--:|
| MJPEG | 10 | 4.6 Mbps | 約 58 KB | 2.4〜2.6 % |
| H.264(NVIDIA H.264 Encoder MFT) | 29 | 3.9〜4.0 Mbps | 約 17 KB | 2.1〜2.3 % |

- H.264 は 3 倍のフレームを、MJPEG より低いビットレートと CPU で送る
- 組み込みブラウザー(localhost)で、コーデック `avc1.4D401E`、640x480、5 秒で 149 フレームを受け取って全部描いた(取りこぼしなし)。キーフレームは約 2 秒ごと
- 画面を離れると H.264 のクライアントが 0 になってエンコードが止まり、約 10 秒後にエンコーダーを解放した
- LAN の IP の http(安全でない接続)では `VideoDecoder` がなく、MJPEG になった。`NotSupportedError` を起こすと、最初のキーフレームのあとで MJPEG に切り替わり、H.264 の接続は閉じた
- H.264 の画面を開いたまま止めても 1.6〜2.6 秒で止まった
- MJPEG 2 台、H.264 2 台、5 秒ごとの静止画を同時に動かしても、定期保存は 49 ms で終わった。H.264 は 28 fps で、エンコーダーは 1 つ
- ほかのプロセスがカメラを使っている間は、保存の失敗の警告が 1 回出て `/health` が 503 になった。カメラが空いたあとの保存で 200 に戻った
- 保存を止めたプロセスで、ほかのプロセスがカメラを使っている間にクライアントをつなぐと、開き直しの間隔は 5 → 10 → 30 秒と伸び、`/health` は 503 のまま(0.1 秒ごとに 444 回)。カメラが空いたあと、最初のフレームで 200 に戻った
- LAN の IP(安全でない接続)の MJPEG を約 50 分開いたまま: 約 3 万枚、1.05 GB、つなぎ直しなし、ブラウザーのヒープ 6 MB
- 接続を壊す中継プログラムで確かめた: 接続を切ると約 2 秒で戻る。断り続けている間は `Reconnecting` のまま。通信だけを止めると 5 秒で `Reconnecting`、15 秒でつなぎ直す。どれもページは読み直さない(MJPEG と H.264 の両方、組み込みブラウザー)

### Windows サービス

発行したフォルダーを LocalSystem のサービス(セッション 0)に登録して、2 回通しで確かめた(2 回目はレビューの指摘を直したあと)。ELECOM 2MP Webcam、YUY2 640x480、毎分の保存。

| 項目 | 結果 |
|:--|:--|
| 保存 | 毎分の保存が予定の時刻から 43〜93 ms(暗くてフレームの間隔が伸びると 108〜678 ms)。12 枚で名前と焼き込みの時刻が秒まで一致 |
| 連続運転 | 約 1 時間、ページを開いたまま(LAN の IP の MJPEG で約 3 万枚)。警告とエラーなし、つなぎ直しなし、メモリー 165 MB |
| 画面 | 全ページ、CSS・JS・フォント、サムネイル、拡大 |
| H.264 | セッション 0 でも NVENC を使える(NVIDIA H.264 Encoder MFT)。カメラのフレームを全部送る(暗いと約 10 fps) |
| 設定の誤り | サービスは起動しない。値の誤りも JSON の書き間違いも、理由がログファイルに出る |
| 自動削除 | 起動時と、時刻を指定したジョブ(現地時刻の 10:30:00 に実行) |
| 強制終了 | 約 60 秒後に再起動して、次の時刻から保存を続ける。開いていたページは自分で読み直し、ライブも戻る |
| 止める | H.264、MJPEG、画面をつないだまま 1.55 秒。誰もいなければ 0.27 秒。次の起動は 0.7 秒で応答 |
| 削除 | サービス、プロセス、ポートが残らない |

手動起動で確かめた。PC の起動時の自動起動は未確認。

### 画面

組み込みブラウザーで、実際のカメラを 5 秒ごとに保存しながら確かめた(画像は CSS で隠して、配置と値だけを見た)。

- **カメラ一覧:** 最新のサムネイル(320x240)、状態、時刻、リンク
- **カメラ:** ライブ 640x480。ページを離れると、サーバーのクライアント数が 0 に戻る。静止画は切り替え・更新・5 秒ごとの自動更新で読み直す
- **保存画像:** 日付の切り替えで URL が変わる。時間ごとの枚数、サムネイル
- **拡大:** ←/→/Home/End、Space で再生(最後で止まる)、Esc で閉じる、先読み、ダウンロード名
- **そのほか:** 存在しないカメラと画像のない日付の表示、状態のページ。コンソールのエラーはない
- **すばやい操作:** ライブの直後に静止画へ切り替える(40 回)、拡大の直後に閉じる(20 回)でエラーにならない。履歴で別のカメラに戻ると、そのカメラの映像になる

✅ 開発用の証明書で、HTTPS と HTTP/2 で `/health` と静止画が取れることを確かめた。

## 💡 分かったこと

- 暗い部屋ではカメラが露出を延ばすので、30 fps の形式でも朝 6 時台の部屋で 16〜17 fps、夕方に約 10 fps になった。H.264 はこれに従い、MJPEG はさらに間引く(カメラ 16.4 fps で 8.3 fps)
- 保存は予定の時刻より後に撮ったフレームを待つので、フレームの間隔が伸びると、ファイルができるのも遅れる(夕方の部屋で 108〜678 ms)
- 届いた順で選ぶと、焼き込みの秒が予定の 1 秒前(`:59`)になることがあった(届くまでの遅れの分)。撮った時刻で選ぶように直した
- `TimeProvider.GetLocalNow()` は `GetUtcNow()` の時計の値に `LocalTimeZone` のオフセットを足す(仮想メソッドではない)。`GetUtcNow()` が現地時刻を返す `LocalTimeProvider` では 2 回足して 9 時間進んだので、`LocalTimeZone` を UTC にした
- ELECOM などの NV12 は、カメラが MJPG で送って Windows がデコードしたもの

## 🐧 Linux
